## 6. Module-specific milestone details  *(~1 min 30 s)*

**Master data**
> One uniform shape for all 40 enumerations: code, translation key, sort order, active flag. They are generated by one procedure, so they can't drift apart. Reference values the rules depend on have fixed IDs that the database protects from being renamed.

**Profile**
> One profile per user account. Salary uses a "disclosure status", so "not disclosed" is different from zero. We tested that zero can't be used as a stand-in for unknown. Resume versions are immutable, so an application always points to the exact resume that was sent. Profile completion is scored per section with weights.

**Jobs and Applications**
> The application pipeline is a rules table plus triggers. You cannot create an application as "joined", skip from "applied" to "joined", or move out of a final status. Every change writes a history row automatically. A placement must fill a headcount slot of the same job, which composite keys enforce. A job-specific shortlist can only belong to that job's own company, which is the recruiter-isolation rule built into the data.

## 7. Key highlights  *(~1 min)*

> Four things we'd like to call out:
>
> 1. **Rules live in the database, not just the app.** For example: recruiters cannot register candidates on someone's behalf; gigs cannot enter the standard job table; history tables reject updates and deletes; every write must have an identified user, or it fails.
> 2. **Self-verifying design.** The checks read the database's own catalog. If someone adds a column without a nullability justification, or uses a reserved word, the build fails. The data dictionary is generated from the database, so it can't go out of date.
> 3. **The gig decision is justified up front.** Gigs will be a separate subsystem because their lifecycle, applicant profile, pricing and external fulfilment are different. Reporting still joins them through shared dimensions. We have a trade-off table covering integrity, reporting and future change.
> 4. **Built for scale from day one.** History tables are partitioned by month. Search uses full-text and trigram indexes. We already checked index usage on a 20,000-candidate sample.

---

## 8. Challenges faced  *(~1 min)*

> - **Deciding the gig model.** Sharing one job table looked simpler, but it needed about ten gig-only empty columns and weakened the no-overlap rule. We chose a separate subsystem and documented the trade-offs.
> - **Business rules that depend on lookup values.** A check constraint can't look up a code, so we reserved fixed IDs for the few system values the rules use, and protected them with a trigger.
> - **Partitioning versus foreign keys.** PostgreSQL requires the partition key in the primary key. So we partitioned the append-only history tables but kept `application` unpartitioned. We'll re-measure that at 1 million profiles.
> - **Our own tests caught real defects.** The audit trigger silently kept the old "updated by" user when none was set. One test passed for the wrong reason. And our runner reported success even when a check failed. All three are fixed, which is why we check *why* a test passes, not just that it passes.
> - **Small-sample performance.** At 20,000 rows, PostgreSQL prefers a table scan over our name-search and keyword-search indexes. We report that honestly and will prove them at 1 million rows.

### Likely panel questions: quick answers

| Question | Answer |
|---|---|
| Why PostgreSQL over MySQL? | Exclusion constraints for non-overlapping periods, row-level security, foreign keys on partitioned tables, partial indexes. MySQL lacks all four. |
| How do you stop a recruiter registering a candidate? | A check constraint: a profile's creator must be the candidate's own account (or the system account for migration). Tested. |
| How is "unknown" different from "not applicable"? | Salary disclosure status (disclosed / not disclosed / not applicable) plus a check that amount, currency and period exist only when disclosed. |
| Can audit or history rows be edited? | No. Triggers reject UPDATE, DELETE and TRUNCATE. Phase 2 also revokes those privileges from the application role. |
| What about deleting a candidate (right to erasure)? | The profile is anonymised in place and soft-deleted, owned child data is hard-deleted, and history keeps only IDs. Event partitions are dropped after the retention period. |
| Where's the evidence? | Run `./run_phase1.sh`; each milestone prints PASS lines and the exact constraint that blocked each bad action. |
