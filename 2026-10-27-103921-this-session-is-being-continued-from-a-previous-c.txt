● They're the four levels of an output schema in the "Control the Output"
  playbook (page 5). From top to bottom:

  ┌───────┬───────┬─────────────────────────────────┬───────────────────────┐
  │ Level │ Name  │          What it holds          │ Example (requirements │
  │       │       │                                 │        docket)        │
  ├───────┼───────┼─────────────────────────────────┼───────────────────────┤
  │       │       │ Sections: the major parts of    │ Scope, Requirements   │
  │ L1    │ Macro │ the output                      │ register, Open        │
  │       │       │                                 │ questions             │
  ├───────┼───────┼─────────────────────────────────┼───────────────────────┤
  │ L2    │ Micro │ Parameters: the fields inside   │ req_id, actor,        │
  │       │       │ each section                    │ priority              │
  ├───────┼───────┼─────────────────────────────────┼───────────────────────┤
  │       │       │ Sub-parameters: allowed values, │ priority → Must ·     │
  │ L3    │ Nano  │  classifications or breakdowns  │ Should · Could ·      │
  │       │       │ inside a parameter              │ Won't                 │
  ├───────┼───────┼─────────────────────────────────┼───────────────────────┤
  │       │       │ Atomic definition of one item:  │ req_id → text,        │
  │ L4    │ Pico  │ data type, format, validation   │ pattern REQ-000,      │
  │       │       │ rule, source                    │ unique                │
  └───────┴───────┴─────────────────────────────────┴───────────────────────┘

  So the order is Macro → Micro → Nano → Pico: from the biggest piece down to
  the smallest.

  In our schema-trees.md, each tree follows that order:
  Requirements register          ← L1 Macro (section)
  ├── priority                   ← L2 Micro (parameter)
  │   └── Must · Should · Could  ← L3 Nano (allowed values)
  └── req_id  [id REQ-[0-9]{3}]  ← L4 Pico (type and format)

  The playbook's depth rules:
  - use at least two levels, never one flat list;
  - normally three or four;
  - go deeper only when one parent has more than about 10–15 children;
  - stop when every item is atomic: one meaning, one type, one rule set.

  All five of our schemas go down to L4 (Pico) and stop there.

> in exception catalogue what is concurrency mean                               

  Ran 1 shell command (ctrl+o to expand)

● In the exception catalogue, concurrency is the category for a specific
  failure: two or more requests arrive at the same moment and touch the same 
  data. Each request is correct by itself, but run together they can break a
  business rule. These bugs never show up when one person tests the app; they
  appear under real traffic.

  The problem: a race condition

  EX-23 (WF-07): an organisation's wallet has 1 credit, and two recruiters click
  "download profile" in the same millisecond.

  Recruiter A                          Recruiter B
  read balance → 1                     read balance → 1
  1 ≥ 1, ok → debit                    1 ≥ 1, ok → debit
  balance = 0                          balance = -1   ❌ rule broken

  Both requests checked the rule ("balance ≥ cost") before either one wrote
  anything. Each check passed, but the combined result is wrong: two profiles
  were given away for one credit.

  The fix: serialise with a row lock

  SELECT balance FROM wallet WHERE id = $1 FOR UPDATE;  -- locks the row
  -- check, debit, write the ledger entry, commit → lock released

  1. A takes the lock first.
  2. B has to wait.
  3. A debits to 0 and commits.
  4. B reads the new balance (0), and its debit is refused.

  The catalogue calls this outcome "serialised; balance never negative". The
  CHECK constraint balance >= 0 is a second safety net.

  The concurrency exceptions in our catalogue

  ┌──────────────────┬────────────────────────────┬────────────────────────┐
  │        ID        │            Race            │         Guard          │
  ├──────────────────┼────────────────────────────┼────────────────────────┤
  │                  │ two candidates marked      │ row lock on the job +  │
  │ EX-13            │ "joined" for the last open │ CHECK joined ≤         │
  │                  │  position                  │ positions              │
  ├──────────────────┼────────────────────────────┼────────────────────────┤
  │ EX-23            │ parallel debits on a small │ wallet row lock +      │

  └──────────────────┴────────────────────────────┴────────────────────────┘

  Why an SDE-2 lists these explicitly

  Any rule that counts things against a limit (credits, seats, positions,
  devices) is a race waiting to happen. A check in the application ("if balance
  ≥ cost") doesn't protect it. The protection has to sit where every request
  passes through: the database, using a lock or a constraint. That's the reason
  the catalogue's last column names a database mechanism, not app code.

  The playbook asks for cancellation, refund, retry, timeout, concurrency and
  external-failure paths. Concurrency is the category juniors most often forget.

> what is state models                                                          

  Ran 2 shell commands (ctrl+o to expand)

● A state model (or state machine) describes an entity that moves through a
  fixed set of stages during its life. It lists every state it can be in, plus
  the transitions: which moves are allowed, who can make them, and what each one
  triggers. Any move that isn't listed is refused.

  Example: our application pipeline

               ┌──────────── rejected ◄──────────┐ (employer, from any active 
  state)
               │                                  │
  applied → shortlisted → interviewing → offered → joined
     │           │             │            │
     └───────────┴─────────────┴────────────┴──► withdrawn  (candidate only)

  ┌────────────┬─────────────┬────────────┬─────────────────────────────────┐
  │    From    │     To      │    Who     │           Side effect           │
  ├────────────┼─────────────┼────────────┼─────────────────────────────────┤
  │ applied    │ shortlisted │ recruiter  │ candidate notified              │
  ├────────────┼─────────────┼────────────┼─────────────────────────────────┤
  │            │             │            │ joined_count + 1; the job       │
  │ offered    │ joined      │ recruiter  │ becomes filled when every       │
  │            │             │            │ position is taken               │
  ├────────────┼─────────────┼────────────┼─────────────────────────────────┤
  │ any active │ withdrawn   │ candidate  │ —                               │
  │  state     │             │ only       │                                 │
  ├────────────┼─────────────┼────────────┼─────────────────────────────────┤
  │ applied    │ joined      │ ❌ not     │ refused (EX-11)                 │
  │            │             │ allowed    │                                 │
  └────────────┴─────────────┴────────────┴─────────────────────────────────┘

  Joined, rejected and withdrawn are terminal states: no move leads out of them.

  Why an SDE-2 models states explicitly

  1. It stops impossible data. Without a state model, someone can write status =
     'joined' on an application nobody interviewed, and every report built on
     the funnel becomes wrong.
  2. The rules live in the database, as data. application_status_transition is a
     table listing the allowed (from, to) pairs, and a trigger refuses
     everything else. Adding a new stage means inserting a row, not shipping
     code.
  3. History comes for free. Each transition is written to
     application_status_history, which is append-only and records when and by
     whom. That's how we get time-to-hire.
  4. It shows you the exceptions. Every arrow that's missing is an exception to
     handle: what happens on an invalid move, when two moves race, or on a
     timeout.

> what is enum                                                                  

● An enum (enumeration) is a type whose value must come from a fixed, named 
  list. Nothing outside that list is accepted.

  priority ∈ { Must, Should, Could, Won't }

  "Must" is valid. "must-ish", "High", "" and "Mst" are rejected.

  Where it appears in our schemas

  In output-schemas.md, enum is one of the L4 types (along with text, id and
  ref), and the L3 column lists its allowed values:

  ┌────────────────┬──────────┬─────────────────────────────────────────────┐
  │   Parameter    │  Type    │             Allowed values (L3)             │
  │                │   (L4)   │                                             │
  ├────────────────┼──────────┼─────────────────────────────────────────────┤
  │ priority       │ enum     │ Must · Should · Could · Won't               │
  ├────────────────┼──────────┼─────────────────────────────────────────────┤
  │ scope_status   │ enum     │ in · out · deferred                         │
  ├────────────────┼──────────┼─────────────────────────────────────────────┤
  │ design_impact  │ enum     │ high · medium · low                         │
  ├────────────────┼──────────┼─────────────────────────────────────────────┤
  │ exception_type │ enum     │ validation · business rule · concurrency ·  │
  │                │          │ …                                           │
  └────────────────┴──────────┴─────────────────────────────────────────────┘

  That's why enums create L3 nodes in the tree and text fields don't: free text
  has no list to expand.

  Why use enums instead of free text
  - Consistency: without them, one person types "High", another "high", another
    "urgent", and a report grouped by priority shows three buckets.
  - Validation: typos are caught when the data is entered, not months later.
  - Easy counting and filtering: "how many Must requirements?" becomes an exact
    query.
  - Clear meaning: the list itself documents what values are possible.

  How the database does it

  PostgreSQL has a built-in CREATE TYPE ... AS ENUM. Talentra deliberately does
  not use it; FR-REF-02 says every fixed set of values is a lookup table
  instead:

  -- PostgreSQL enum (not used)
  CREATE TYPE priority AS ENUM ('must', 'should', 'could');

  -- Lookup table (what we use)
  work_mode(id, code, ui_label_id, is_active, sort_order)
  job_requirement.work_mode_id → FK → work_mode.id

  Why an SDE-2 picks the lookup table:

  ┌─────────────────────────┬────────────────────┬──────────────────────────┐
  │          Need           │  PostgreSQL ENUM   │       Lookup table       │
  ├─────────────────────────┼────────────────────┼──────────────────────────┤
  │ Add a value             │ ALTER TYPE, a      │ INSERT a row             │
  │                         │ schema change      │                          │
  ├─────────────────────────┼────────────────────┼──────────────────────────┤
  │ Retire a value          │ can't remove it    │ is_active = false, old   │
  │                         │                    │ rows stay valid          │
  ├─────────────────────────┼────────────────────┼──────────────────────────┤
  │ Translate the label     │ ❌                 │ ✅ via ui_label_id       │
  │ (Hindi, Tamil…)         │                    │                          │
  ├─────────────────────────┼────────────────────┼──────────────────────────┤
  │ Control display order   │ ❌                 │ ✅ via sort_order        │
  ├─────────────────────────┼────────────────────┼──────────────────────────┤
  │ Values readable by the  │ awkward            │ a normal SELECT          │
  │ UI and reports          │                    │                          │
  └─────────────────────────┴────────────────────┴──────────────────────────┘

  The rule of thumb: use a real ENUM only for small internal lists that will
  never change and are never shown to users. Anything a user sees, or a business
  might change, belongs in a lookup table.
